# Spec 2 — Agent-Agnostic Core (design)

**Date:** 2026-05-28
**Status:** Approved, awaiting plan
**Branch:** `development`
**Predecessor:** [Spec 1 — Consistency & Correctness](2026-05-27-lfg-cleanup-consistency-design.md), shipped to `main` as PR #5 (commit `6d11ea2`).
**Successor:** Spec 3 — Graceful work-aware archival (deferred).

## Context

Spec 1 made the shipped LFG product internally consistent on its existing architecture. Spec 2 makes the product **agent-agnostic**: any agent — Codex, Cursor, Claude Code, Augment, Hermes, OpenClaw, or a fresh team-of-agents implementation — should be able to pick up an LFG-installed project from a single neutral entry point, with a defined protocol for dispatching subagents and a small set of deterministic commands for things that should not be eyeballed by an LLM.

Today, the per-tool rule directories (`.claude/rules/`, `.augment/rules/`) ship the same content twice. Any new tool means a third copy. There is no neutral entry point — tools without their own rules-loading convention get nothing. The "subagent" idea exists only as a single line in `log-file-maintenance.md` ("subagents skip SESSION END"); there is no real protocol.

Spec 2 addresses all three.

This design incorporates a code-owl plan review (13 risks identified, mitigations folded inline).

## Goals (in priority order)

1. **One canonical source** for rule content. AGENTS.md is the neutral artifact any agent reads.
2. **Per-tool depth** is preserved via generated rule directories — no regression on Claude Code or Augment.
3. **Subagents have a real protocol**: identity signal, context priming, staged writes promoted by the lead.
4. **Deterministic commands** (`lfg generate`, `lfg prime`, `lfg promote`) replace ad-hoc LLM behavior only where determinism actually matters.
5. **Drift hazards eliminated** — no committed generated directories that need a "regenerate or fail" tripwire (Spec 1's lesson).

## Non-goals (explicitly deferred)

- **Graceful, work-aware archival** → Spec 3.
- **Tools beyond Claude Code + Augment getting tool-specific dirs.** Codex, Cursor, etc. read AGENTS.md natively; no new per-tool dirs in this spec.
- **CLI surface beyond `generate`, `prime`, `promote`.** Other deterministic-command candidates (`lfg tokens`, `lfg session-start`) are deferred.
- **Multi-agent concurrent-coordination protocol** (STATE.md "Active Work" formalization). The subagent protocol here is dispatched-within-a-run only.
- **Topic-aware context filtering** in `lfg prime`. Removed during review (LLM work, not deterministic).

## Decisions (locked with user)

- AGENTS.md role: **single canonical source, per-tool generated.**
- Canonical shape: **fragments are canonical; AGENTS.md is concatenated from them.**
- Subagent focus: **dispatched subagents within a single run.**
- CLI scope: **targeted** — only commands the new architecture needs (`generate`, `prime`, `promote`).

## Architecture

```
product/
├── rules/                       # canonical fragments (human-edited)
│   ├── log-file-maintenance.md
│   ├── status-update.md
│   ├── update-planning-docs.md
│   └── token-usage.md
├── AGENTS.md                    # generated; COMMITTED (one file, manageable diff)
├── install-templates/           # tool-specific wrappers requiring fixed filenames
│   └── claude/project_instructions.md.tmpl
└── scripts/
    └── lfg.py                   # gains: generate, prime, promote
```

- **`product/rules/`** contains one set of fragments. Each fragment has YAML frontmatter declaring its `order`, `targets`, and `summary`. The canonical text is tool-neutral.
- **`product/AGENTS.md`** is generated by `lfg generate` and committed. Single file, single PR-diff cost per edit, CI-gated against drift by `lfg generate --check`.
- **No `install-payload/` directory.** Per-tool rule directories are generated at *install time* on the user's machine — not in the source repo. This is the structural decision that prevents recreating Spec 1's install-vs-update divergence.
- **`product/install-templates/`** holds tool-specific wrappers for files that demand fixed filenames (e.g., Claude's `project_instructions.md`). Rendered at install time with paths interpolated from `.logfile-config.yml`.

### Fragment frontmatter (replaces `_index.md`)

```yaml
---
fragment: log-file-maintenance
order: 10
targets: [agents_md, claude_rules, augment_rules]
summary: Always-active rules for log maintenance.
---
```

- `order`: integer; smaller renders first.
- `targets`: list from a closed set: `agents_md`, `claude_rules`, `augment_rules`. (New targets get added here, not by walking new directories.)
- `summary`: one-line description used in AGENTS.md's section index.

Fragment renames are safe: `order` is independent of filename.

### Fragment content rules

- **No literal `.claude/...` or `.augment/...` paths** in fragments. Path references resolve via `.logfile-config.yml → paths.<key>` with `logs/<key>` fallback — extending Spec 1's convention.
- The Claude-Code-specific `project_instructions.md` (Claude expects this exact filename) is the *one* tool-specific artifact; it stays as a wrapper under `install-templates/` that includes AGENTS.md content at install time.

## Components

### `lfg generate [--check]`

Pure transformation:
1. Scan `product/rules/*.md`. Parse each fragment's YAML frontmatter.
2. Validate: `fragment`, `order`, `targets` required; `targets` is a subset of the closed set.
3. Sort by `order`.
4. Concatenate fragments tagged `agents_md` into `product/AGENTS.md`, headed by frontmatter, a "Read this first" block, an "Available commands" block, a section index, and `## <fragment>` headings.
5. Compute token count (chars/4); fail if **> 4,500**. (Budget history: design 3,000 -> measured 3,772 -> 4,000 (T6) -> T11 contract block pushed it to 3,999/4,000 with zero slack -> 4,500 (T13) for editing headroom. Each bump preserved the gate purpose: bound growth, not enforce a magic number.)
6. Write LF + UTF-8, no BOM, single trailing newline.

`--check` mode: re-render to a temp file and diff against the committed AGENTS.md. Exit non-zero on any difference. Used by CI.

**Idempotent**: same inputs → byte-identical output every time.

### `lfg prime [--n N] [--json]`

Emits a context digest for a subagent:
1. Print the literal header `LFG_SUBAGENT_PRIME` (the **role-identity signal** — see §Subagent protocol).
2. Read STATE.md (via `paths.state`); include its Current Context + Last Session in full.
3. Read CHANGELOG.md (via `paths.changelog`); include the last `--n N` (default 5) entries under "Unreleased".
4. Append the resolved `.logfile-config.yml` paths block (for the subagent to know where files live).
5. With `--json`, the same content as a structured object.

No `--topic` flag. No fuzzy relevance. Deterministic, fast (sub-100ms in practice).

### `lfg promote <subagent-id>`

Lead-only verb. Reads `.lfg/staged/<subagent-id>/` (located at the **user's project root**, alongside `logs/` and `.logfile-config.yml`) and merges into canonical:
- Appends `changelog.md` (if present) under CHANGELOG.md's "Unreleased" section, in the correct category.
- Appends `devlog.md` (if present) to DEVLOG.md's Daily Log.
- Writes a one-line audit trail of the promote (timestamp + subagent-id) to `.lfg/promoted.log`.
- Removes the staged directory on success.

The `.lfg/` directory is created lazily by `lfg promote` (or the lead manually) and should be added to the project's `.gitignore` by default — staged subagent output is ephemeral working state, not history.

Idempotent in spirit — running on an empty/already-promoted ID is a no-op with a clear message.

### Installer / update changes

- At install time, the installer **generates per-tool rule dirs from fragments**:
  - For each fragment whose `targets` includes `claude_rules`: copy to `.claude/rules/<fragment>.md`.
  - Same for `augment_rules` → `.augment/rules/`.
- Render `install-templates/claude/project_instructions.md.tmpl` with values from `.logfile-config.yml` → `.claude/project_instructions.md`.
- Copy `product/AGENTS.md` (already generated, committed) to the project root.
- `update.*` mirrors this — installs from the same source path; no separate update logic.

## Subagent protocol

### Identity signal — the missing piece

`lfg prime` emits an `LFG_SUBAGENT_PRIME` header at the top of its output. **Any agent whose initial context contains that marker IS a subagent and follows the subagent contract.** The lead establishes the role by including the digest verbatim when dispatching. There is no self-detection.

The rule fragment for `log-file-maintenance.md` carries the matching instruction: "If your initial context contains `LFG_SUBAGENT_PRIME`, you are a subagent. Follow the subagent contract below."

### Lead's contract

- **Before dispatch**: run `lfg prime [--n N]` and paste the output verbatim into the subagent's prompt. The header establishes the role.
- **On report receipt**: review the subagent's staged entries in `.lfg/staged/<id>/`, then run `lfg promote <id>` to merge them into canonical CHANGELOG/DEVLOG.

### Subagent's contract

- **Read** the primed digest. Do not read the full CHANGELOG/DEVLOG/STATE unless directed.
- **Never** modify STATE.md (Spec 1 already established SESSION END is lead-only).
- **Never** write directly to CHANGELOG.md or DEVLOG.md.
- **Staged writes**: when your work warrants a CHANGELOG or DEVLOG entry, write it to `.lfg/staged/<your-id>/changelog.md` and/or `.lfg/staged/<your-id>/devlog.md`. The lead will promote.
- **No `lfg prime` self-call**: there is no `--topic` flag. If you need more context, ask the lead.

### Why staged writes (not verbal handoff)

Verbal-only handoff loses subagent-local detail by the time the lead receives the report — especially for long-running subagents where the lead's own context drifts. Staged writes preserve the subagent's working context while keeping the lead as source of truth.

## AGENTS.md content

The [agents.md community convention](https://agents.md) has no required schema; tools consume AGENTS.md as a system-prompt addendum. The structure below is for readability:

1. **YAML frontmatter** — `doc: AGENTS`, `version`, `related:` map pointing at STATE/CHANGELOG/DEVLOG. Continues Spec 1's frontmatter link graph.
2. **"Read this first" block** — three sentences max: read `STATE.md` for the now, `CHANGELOG.md` Unreleased for what changed, `DEVLOG.md` Daily Log for why.
3. **"Available commands" block** — one line per `lfg` subcommand: `validate`, `prime`, `promote`, `status`, `generate`.
4. **Section index** — one line per fragment with its `summary`.
5. **Fragments** — concatenated in `order`, each prefixed with `## <fragment-name>`.

**Hard token-budget gate**: `lfg generate` computes the rendered token count and fails the build if it exceeds **4,500 tokens** (chars/4 heuristic). Not a target — a test.

## Testing

- **`test_lfg_generate_idempotent`** — two consecutive `lfg generate` runs produce byte-identical AGENTS.md.
- **`test_generate_check_zero_diff_on_main`** — `lfg generate --check` returns 0 with no output on a clean checkout. CI runs this on every PR.
- **`test_agents_md_under_budget`** — rendered AGENTS.md token count ≤ 4,500. Hard fail.
- **`test_line_endings_canonical`** — AGENTS.md is LF, no BOM, single trailing newline; generator and asserter must agree byte-for-byte.
- **`test_no_per_tool_paths_in_fragments`** — fragments contain no literal `.claude/` or `.augment/` substrings (excluding code blocks that are clearly examples).
- **`test_frontmatter_schema_valid`** — every fragment has required keys (`fragment`, `order`, `targets`), `targets` ⊆ the closed set.
- **`test_install_drops_agents_md_and_rules`** — after install: AGENTS.md at project root, and every fragment whose `targets` includes `claude_rules` (resp. `augment_rules`) lands in the right per-tool dir.
- **`test_lfg_prime_emits_subagent_marker`** — output contains the `LFG_SUBAGENT_PRIME` header and STATE content.
- **`test_lfg_promote_appends_then_clears`** — given a seeded `.lfg/staged/<id>/changelog.md`, `lfg promote <id>` appends to canonical CHANGELOG and removes the staged dir; second run is a no-op.
- **`test_cold_read_workflow`** — fixture script reads AGENTS.md, follows its "Read this first" pointers to STATE/CHANGELOG/DEVLOG, and asserts each file exists and parses. Surrogate for "a cold agent could orient using AGENTS.md alone."

## Self-application (CHANGELOG discipline for Spec 2's own work)

Editing a fragment changes:
- the fragment itself (canonical source)
- `product/AGENTS.md` (generated, committed)
- (at install time, on every user's machine) the per-tool rule files

The CHANGELOG entry for such a change references **only the fragment path**. The regenerated AGENTS.md is implicit (covered by the CI check); the per-tool files don't exist at commit time. Add this rule to the CHANGELOG entry-format guidance in `log-file-maintenance.md`.

## Acknowledged trade-off

**Python becomes a build-time dependency for LFG contributors.** Spec 1 removed PyYAML to keep LFG runtime-zero-dep — that property is preserved for *users* of LFG (the installer, validators, hook still run, but the user need not regenerate). LFG *contributors* need Python 3.11+ to run `lfg generate` before committing fragment changes. Mitigations:

- Document in CONTRIBUTING.md.
- Provide a pre-commit hook (`.git/hooks/pre-commit`) in the contributor setup that auto-runs `lfg generate` on staged fragment changes.
- CI runs `lfg generate --check` so forgetting still fails review.

## Risks accepted

- **One generated file committed (`AGENTS.md`)**. The CI check catches drift; the diff cost per edit is one file's worth, not a directory. Considered acceptable given the alternative (regenerate at install time) requires Python at install time, which is a larger regression on user-facing zero-dep.
- **Subagent protocol applies only inside a single run.** Concurrent multi-agent coordination on the same repo (different humans + their agents) is out of scope; STATE.md's "Active Work" block remains aspirational until a future spec.
